# なぜ設計が重要なのか？

## 設計がないとこうなる
- 🔥 **コードが燃える** - 修正のたびにバグが増える
- 😵 **理解不能** - 他人（未来の自分含む）が読めない
- 🐌 **開発速度低下** - 新機能追加に時間がかかる
- 💸 **コスト増大** - メンテナンスに莫大な時間とお金

---

# SOLID原則 - 良い設計の基本

## S - Single Responsibility Principle
**単一責任の原則**
- 1つのクラスは1つの責任だけを持つ
- 変更理由は1つだけであるべき

## O - Open/Closed Principle  
**オープン・クローズドの原則**
- 拡張に対して開いている
- 修正に対して閉じている

---

# SOLID原則（続き）

## L - Liskov Substitution Principle
**リスコフの置換原則**
- 派生クラスは基底クラスと置換可能

## I - Interface Segregation Principle
**インターフェース分離の原則**
- 使わないインターフェースに依存しない

## D - Dependency Inversion Principle
**依存性逆転の原則**
- 抽象に依存し、具体に依存しない

---

# デザインパターン基礎

## よく使われるパターン

### 生成パターン
- **Singleton** - インスタンスを1つに制限
- **Factory** - オブジェクト生成を抽象化

### 構造パターン
- **Adapter** - インターフェースを変換
- **Decorator** - 機能を動的に追加

### 振る舞いパターン
- **Observer** - イベント通知の仕組み
- **Strategy** - アルゴリズムを切り替え可能に

# 良いコードの特徴

## 読みやすさ
\`\`\`javascript
// 悪い例
function calc(a, b, t) {
  return t === 1 ? a + b : a * b;
}

// 良い例
function calculateTotal(price, quantity, operation) {
  if (operation === 'add') {
    return price + quantity;
  }
  return price * quantity;
}
\`\`\`

# アーキテクチャパターン

## レイヤードアーキテクチャ
- **プレゼンテーション層** - UI処理
- **ビジネス層** - ビジネスロジック
- **データアクセス層** - データベース操作

## MVC パターン
- **Model** - データとビジネスロジック
- **View** - 表示処理
- **Controller** - ユーザー入力の制御

---

# 実践的な設計手法

## ドメイン駆動設計（DDD）
- **ビジネスドメインを中心**とした設計
- **ユビキタス言語**で開発者と業務担当者が対話

## テスト駆動開発（TDD）
1. **Red** - 失敗するテストを書く
2. **Green** - テストを通すコードを書く
3. **Refactor** - コードを改善する

---

# 設計の悪臭（コードスメル）

## 要注意サイン
- 📏 **長すぎるメソッド** - 1つのメソッドが100行超え
- 🎯 **神クラス** - 何でもできる巨大クラス
- 📝 **重複コード** - コピペの繰り返し
- 🔄 **循環依存** - お互いを参照するクラス

## 対処法
- **リファクタリング**で継続的改善
- **コードレビュー**で早期発見

---

# まとめ：良い設計への道

## 基本原則を守る
1. **SOLID原則**を理解し適用
2. **デザインパターン**を適切に使用
3. **可読性**を最優先に

## 継続的改善
- 小さなリファクタリングを積み重ね
- チーム全体で設計品質を意識
- **完璧を目指さず、より良いを目指す**
